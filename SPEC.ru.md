# Zerkalo — техническое задание

Зеркало экрана телефона на телевизор через Android-приставку по домашнему Wi-Fi. Одно приложение
с двумя ролями: передатчик (телефон) и приёмник (приставка). Без аккаунтов, облака и интернета,
устройства общаются напрямую.

## Стек

- Kotlin + Jetpack Compose, один модуль `:app`, пакет и `applicationId` — `xx.zerkalo`
- minSdk 28 / targetSdk 36, без нативного кода
- Один universal APK без разбиения по ABI: нативного кода нет, поэтому отдельные сборки не нужны
- Захват: `MediaProjection` + `VirtualDisplay`
- Кодирование и декодирование: аппаратный `MediaCodec`, H.264 и H.265
- Сеть: TCP для управления, UDP для видео и поиска приёмников, собственный протокол
- Настройки — `SharedPreferences`, базы данных нет
- `shared/updater` и `shared/about` подключаются через `sourceSets`, как в остальных проектах
- Языки интерфейса: en, ru, uk. Имя: Zerkalo / Зеркало / Дзеркало

## Целевые параметры

- Передатчик: Samsung A36. Приёмники: Tox3 и Ugoos Cube X3 Pro
- Содержимое: видео и фото, приоритет у плавности, а не у минимальной задержки
- Задержка «экран телефона → телевизор»: цель ≤ 200 мс на Wi-Fi 5 ГГц
- Один передатчик на приёмник в один момент времени

## Что не входит в первую версию

- Звук. Отдельный этап после того, как заработает видео
- Шифрование потока. PIN защищает от чужого подключения, но не от перехвата внутри сети:
  видео идёт открыто, а четырёхзначный PIN подбирается по записи обмена
- Автозапуск приёмника. Приёмник всегда открывают вручную из лаунчера приставки
- Автоматическое переподключение после обрыва
- Показ DRM-видео и экранов с `FLAG_SECURE`: система отдаёт вместо них чёрный экран

## Роли

Роль хранится в настройках и переключается там же. При первом запуске значение подставляется по
устройству: `UiModeManager` сообщает телевизор или есть `FEATURE_LEANBACK` — приёмник, иначе
передатчик. Переключение роли завершает текущую сессию.

Манифест, как в PhotoBox: `LEANBACK_LAUNCHER`, `android:banner`, `touchscreen` и `leanback` с
`required="false"`. Весь интерфейс приёмника управляется пультом.

## Сценарий работы

1. На приставке открывают Zerkalo. На экране имя приёмника и PIN из 4 цифр.
2. На телефоне открывают Zerkalo и видят список найденных приёмников. Если приёмника нет в
   списке, вводят IP вручную.
3. При первом подключении вводят PIN. Дальше телефон подключается одним нажатием.
4. Android спрашивает разрешение на захват экрана. Это происходит при каждом запуске трансляции
   и не обходится.
5. Телевизор показывает экран телефона, по бокам или сверху чёрные поля, пропорции сохраняются.
6. Трансляция останавливается кнопкой в приложении или в уведомлении, либо при выходе из
   приёмника. Приёмник возвращается на экран ожидания.

## Сеть

| Порт | Протокол | Назначение |
|---|---|---|
| 47700 | TCP | управление, слушает приёмник |
| 47701 | UDP | анонсы приёмника, слушает передатчик |
| 47702 | UDP | видео, слушает приёмник |

Все числа в big-endian. Строка — `u16` длина и байты UTF-8. Версия протокола `PROTOCOL_VERSION = 1`.

### Поиск приёмников

Приёмник на экране ожидания раз в 2 секунды шлёт широковещательный UDP на адрес своей подсети и
на `255.255.255.255`:

```
magic "ZRKL" | u8 version | u8 type=0x01 | 16 байт receiverId | u16 controlPort | string name
```

Приёмник считается пропавшим после 7 секунд тишины. Передатчик держит `MulticastLock`, пока
открыт список приёмников, потому что без него часть телефонов отбрасывает широковещательные
пакеты. Если роутер изолирует клиентов, анонсы не дойдут, и ручной ввод IP тоже не поможет: нужна
сеть без изоляции.

### Канал управления

Сообщение TCP: `u16 type | u32 length | payload`, длина не больше 64 КиБ. Передатчик открывает
соединение первым.

| type | Направление | Сообщение | Поля |
|---|---|---|---|
| 0x01 | S→R | HELLO | `u8 version`, 16 байт `senderId`, `string name`, 16 байт `nonceS`, `u8 mode` (0 PIN, 1 токен) |
| 0x02 | R→S | CHALLENGE | 16 байт `receiverId`, 16 байт `nonceR` |
| 0x03 | S→R | AUTH | 32 байта `proof` |
| 0x04 | R→S | AUTH_OK | `u8 codecs` (бит 0 H.264, бит 1 H.265) |
| 0x05 | S→R | CONFIG | `u16 configId`, `u8 codec`, `u16 width`, `u16 height`, байты CSD |
| 0x06 | R→S | READY | `u16 configId` |
| 0x07 | R→S | KEYFRAME_REQUEST | нет |
| 0x08 | оба | PING | нет |
| 0x09 | оба | BYE | нет |
| 0x0F | R→S | ERROR | `u8 code` (1 занято, 2 неверный PIN, 3 неизвестный токен, 4 версия) |

Значения `codec`: 0 — H.264, 1 — H.265.

### Сопряжение

```
pairKey = HMAC-SHA256(key = PIN, "zerkalo-pair" | nonceS | nonceR)
proof   = HMAC-SHA256(key = K,   "zerkalo-auth" | nonceS | nonceR)
```

`K` — это `pairKey` в режиме PIN и сохранённый токен в режиме токена. При успешном вводе PIN обе
стороны запоминают `pairKey` как токен: передатчик по `receiverId`, приёмник по `senderId`. Сам PIN
и токен по сети не передаются.

- Новый PIN генерируется при каждом запуске приёмника и после 3 неверных попыток подряд.
- После 3 неверных попыток приёмник 10 секунд отвечает `ERROR 2`, не проверяя PIN. Без этой паузы
  четыре цифры перебираются по сети за минуты: смена PIN сама по себе перебор не замедляет.
- Ответ `3` (неизвестный токен) заставляет передатчик забыть токен и спросить PIN.
- В настройках приёмника есть список запомненных передатчиков с удалением.
- Приёмник принимает только одну сессию, остальным сразу отвечает `ERROR 1`.

Сессия жива, пока идут PING: раз в секунду с каждой стороны, обрыв через 4 секунды тишины.

### Видео

Датаграмма не больше 1400 байт, поэтому не фрагментируется на уровне IP. Приёмник принимает её
только с адреса, с которого открыт канал управления.

```
Видео, S→R, заголовок 16 байт:
u8 type=0x10 | u8 flags (бит 0 ключевой кадр) | u16 configId | u32 frameId |
u16 fragIndex | u16 fragCount | u32 ptsMs | payload до 1384 байт

NACK, R→S:
u8 type=0x11 | u8 count | u32 frameId | u16 fragIndex × count
```

Кадр — один выходной буфер `MediaCodec`. CSD (`SPS`, `PPS`, `VPS`) идут только через CONFIG, то
есть надёжным каналом. Кадры шлются пачками по 32 пакета с паузой 1 мс, иначе большой ключевой кадр
переполняет буфер точки доступа.

**Потери.** Ключевой кадр занимает сотни пакетов, и при потере 1% почти каждый такой кадр лишился
бы хотя бы одного пакета. Запрос нового ключевого кадра не помог бы, потому что он теряется так же.
Поэтому нужен выборочный повтор:

- Передатчик хранит пакеты последних 32 кадров.
- Приёмник находит дыры по номерам и шлёт NACK. Повторы идут каждые 20 мс, не больше 3 раз на кадр.
- Если кадр не собрался к своему сроку, приёмник выбрасывает его, держит на экране последний
  хороший кадр и шлёт KEYFRAME_REQUEST, не чаще раза в 500 мс.
- Пока не придёт ключевой кадр, остальные кадры не декодируются, поэтому артефактов на экране нет.

**Показ.** Приёмник буферизует кадры на `PLAYOUT_DELAY_MS = 80`. Смещение часов считается как
минимум `время прихода − ptsMs` за скользящее окно, кадр показывается через
`releaseOutputBuffer(index, renderTimeNs)`. Срок сборки кадра — момент его показа.

## Захват и кодирование (передатчик)

Порядок запуска важен, иначе Android 14+ завершает приложение с ошибкой:

1. Подключение и сопряжение, чтобы ошибка PIN не тратила разрешение на захват.
2. Запрос согласия: на API 34+ с `MediaProjectionConfig.createConfigForDefaultDisplay()`, поэтому
   выбрать можно только весь экран.
3. `startForegroundService`, затем `startForeground` с типом `mediaProjection`.
4. `getMediaProjection`, регистрация `MediaProjection.Callback`, затем `createVirtualDisplay`.

Токен и `createVirtualDisplay` на Android 14+ одноразовые. При повороте экрана `VirtualDisplay` не
пересоздаётся, а получает `resize` и `setSurface` от нового кодировщика.

Размер потока — экран телефона, вписанный в 1920×1080 с сохранением пропорций и выровненный по
требованиям кодека (`getWidthAlignment`, `getHeightAlignment`). Портрет A36 даёт примерно 498×1080,
что снижает битрейт и не упирается в ограничения декодера по высоте.

При смене ориентации (`DisplayManager.DisplayListener`) кодировщик пересоздаётся, `configId`
увеличивается, приходит новый CONFIG, а приёмник пересоздаёт декодер и отвечает READY. Пакеты со
старым `configId` отбрасываются.

Параметры кодировщика:

| Параметр | Значение |
|---|---|
| `KEY_BITRATE_MODE` | VBR |
| `KEY_BIT_RATE` | H.264: 4, 8 или 16 Мбит/с по настройке качества. H.265: 0,65 от этого |
| `KEY_FRAME_RATE` | 30 или 60 по настройке |
| `KEY_I_FRAME_INTERVAL` | 2 секунды |
| `KEY_REPEAT_PREVIOUS_FRAME_AFTER` | 100 мс, чтобы статичное фото не оставляло поток пустым |
| `KEY_PRIORITY` | 0 (реальное время) |

Кодек берётся из настройки, если его поддерживают обе стороны и кодировщик сконфигурировался. Иначе
H.264. Используются только аппаратные кодеки: на API 29+ `isHardwareAccelerated`, на API 28 по
исключению программных имён.

Передатчик держит `WifiLock` в режиме `WIFI_MODE_FULL_LOW_LATENCY` (ниже API 29 — `HIGH_PERF`),
иначе энергосбережение Wi-Fi даёт рывки задержки. Уведомление foreground service содержит кнопку
«Стоп». `onStop` у `MediaProjection` завершает сессию.

## Приём (приёмник)

- Полноэкранная `SurfaceView`, размер под пропорции потока, `keepScreenOn`, `WifiLock`
- Декодер получает CSD как буфер с `BUFFER_FLAG_CODEC_CONFIG`, поэтому код одинаков для обоих кодеков
- На API 30+ включается `KEY_LOW_LATENCY`, если декодер его поддерживает
- AUTH_OK сообщает реальные кодеки приставки по `MediaCodecList`

## Зацепки под звук

Звук добавляется отдельным этапом, но формат протокола под него уже оставлен, поэтому видео менять
не придётся и версия протокола не вырастет:

- **Согласование.** В маске кодеков AUTH_OK бит 4 означает Opus (`CODEC_AUDIO_OPUS`). Передатчик
  шлёт звук только приёмнику, который выставил этот бит, поэтому старый приёмник звука не увидит.
- **Настройка.** Тип управляющего сообщения 0x0A зарезервирован под AUDIO_CONFIG: кодек, частота,
  каналы, CSD.
- **Данные.** Тип датаграммы 0x12 (`PACKET_AUDIO`), тот же порт 47702. Приёмник разбирает датаграммы
  по первому байту, поэтому второго сокета не нужно.
- **Синхронизация.** `ptsMs` видео и звука считаются от одних и тех же часов сессии, а `PlayoutClock`
  пишется как общий для обоих потоков, а не только для видео.
- **Захват.** `AudioPlaybackCapture` работает от того же объекта `MediaProjection`, повторного запроса
  разрешения не будет. Нужны Android 10+ на передатчике (A36 подходит), разрешение `RECORD_AUDIO` и
  тип foreground service `mediaProjection|microphone`. Приставке на Android 9 это не мешает: она
  только воспроизводит.
- **Ограничение.** Приложения могут запретить захват своего звука, тогда он будет только на телефоне.

## Структура кода

```
xx.zerkalo
  Common.kt            все константы протокола и тайминги, без зависимостей от Android
  net/                 Protocol, Pairing, Discovery, ControlChannel
  video/               Fragmenter, FrameAssembler, RetransmitBuffer, PlayoutClock
  sender/              SenderService, ScreenEncoder
  receiver/            ReceiverSession, FrameDecoder
  settings/            AppSettings, Locales
  ui/                  экраны Compose
```

`net` и логика `video` не зависят от Android и покрываются JVM-тестами: разбор сообщений с
контрольным байтовым образцом, сопряжение, сборка кадров с потерями и перестановками, выбор дыр для
NACK, смена `configId`.

## Этапы

1. Каркас: Gradle, манифест, скрипты версии, роль в настройках, updater и about, иконки.
2. Протокол и сопряжение с JVM-тестами.
3. Поиск приёмников, канал управления, экран PIN.
4. Видео H.264 без обработки потерь: картинка на телевизоре.
5. Устойчивость: NACK, запрос ключевого кадра, показ по часам, поворот экрана.
6. H.265, настройки качества и частоты кадров.
7. Позже: звук.
8. Позже: не давать экрану передатчика гаснуть по таймауту во время трансляции, разрешив ему притухать (`SCREEN_DIM_WAKE_LOCK`).
